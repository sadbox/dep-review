# dep-review v0.2: build spec

This file is the single source of truth for the v0.2 rebuild. Where the
design notes it was derived from disagree with it, this file wins.

## 1. Goal and threat model

Merge Dependabot updates without a person when a short list of positive
facts holds, fast for security fixes, and clearly better than merging
unread. In scope: commodity attacks (a compromised maintainer account, a
new install script, credential theft, an obvious obfuscated payload, a
re-pointed Action tag, a malicious new transitive dependency, cheap prompt
injection). Out of scope: an attacker who studies the gate and crafts
input against its readers. Anything the gate does not recognise goes to a
person; it never gets its own detector.

## 2. The rule

Default outcome is `person`. Deterministic code grants a merge from facts
taken from authoritative sources. The model reads code and can only veto.
Deterministic code never tries to understand what a dependency's code
does: no reachability, no attribution, no build simulation. One kind of
update merges with nothing read by anyone: a reusable workflow of the
gate owner's own repositories, on the owner's ruling (amendment 60).

Three outcomes:

- `merge`: every fact holds, no veto, required checks green, and the
  default branch has not changed a file of the pull request (amendment
  62).
- `wait`: only time, CI or a retry is missing. Re-evaluated automatically.
- `person`: a fact is false or unknown, or the model raised a veto.

Invariants, each with a unit test in `internal/allow`:

1. No model output makes a decision more permissive than "no veto".
2. A fact that is false or was never gathered is `person`, and only a fact
   that holds contributes to `merge`. A fact whose source was asked and
   did not answer is `wait` (amendment 1).
3. `Decide` is a pure function of (facts, policy, now). No I/O.
4. Reasons come from a closed set of constants; no free text decides.

## 3. Facts

Per pull request:

| Fact | Meaning | Source |
|---|---|---|
| Identity | Dependabot's alone, base is the default branch, head current | existing `internal/classify` |
| Shape | only that ecosystem's manifest and lock files changed, each a plain file at both commits (amendment 32), and only version or hash tokens | exact line shapes, or the real tool's reading of base and head |
| ChecksConfigured | the default branch has an active rule that requires a status check other than the gate's own (amendment 33) | GitHub `rules/branches` |

Per update (every package the PR moves, computed from base and head
manifests, never from the PR title, body, labels or Dependabot metadata):

| Fact | Meaning |
|---|---|
| Known | the name is a dependency at the base commit, or matches the policy list (Docker: matches the list, amendment 3) |
| Listed | the name matches the policy list |
| NewName | the name is absent at base |
| Increase | `to` is a plain release above `from`; Go: a listed module may also move to a higher pseudo-version (amendment 24) |
| Major | the leading version component changed; for an image that is the tag's, and a refresh under an unchanged tag is never a major, whatever the tag (amendment 50) |
| Indirect | the repository's own manifest shows it does not declare the dependency: Go, the require line is marked `// indirect`; npm, the name is in none of the root package's dependency maps (amendment 23) |
| Bound | the pinned hash, commit or digest equals what the registry reports now (an action: the repository is also the one whose IDs `actions.lock` records, or for an own workflow the policy does, amendment 60) |
| FirstSeen | when the version became public, by a clock the publisher cannot set; where the registry has none, when the gate first evaluated the pin (amendment 38) |
| NameCreated | when the package name first appeared (new names only) |
| Clean | still published; not retracted, yanked or deprecated; no malware advisory; no advisory on `to` that `from` did not have (an action used from a directory of its repository is asked about under the repository's name and its own, amendment 47; an own workflow needs no published release, so for it Clean is the advisories alone, amendment 60) |
| NoRegress | no new or changed install script, and in an npm tarball none that is gone either (amendment 25); a script is the command `package.json` gives a hook, and the files that command or a `binding.gyp` runs are not compared, apart from `.gypi` files (section 6, amendment 58); in an npm repository that turns install scripts off this part holds by that fact (amendment 59); provenance identity (source repository and builder) not lost; Actions: the new commit descends from the old one on the default or a release branch and the tag resolves to it; an own workflow: on the default branch, and no other (amendment 60) |
| SecurityFix | GitHub's Advisory Database has a reviewed, non-withdrawn advisory that affects `from`, does not affect `to`, and names `to` as first patched version; Go and npm only: it never holds for an image (amendment 3) or for an action, whose tag can be moved after the advisory was reviewed (amendment 48) |
| Superseded | Docker only: the registry serves another digest under the pinned tag now (amendment 2) |
| Own | Actions only: the update moves the commit pin of a reusable workflow in a repository on the policy's `own_workflows` list (amendment 60) |
| Read | `full`, `partial`, `none`, `refused`, or `not-applicable` (Docker, and an own workflow) |
| Veto | nil, or a category and quoted lines |

Each fact records `ok`, `unavailable`, `value` and `source`, so the PR
comment can show why. A fact with no source was never gathered.

## 4. Decision table

Person, immediately, when any of: Identity, Shape, ChecksConfigured,
Increase, Bound, Clean or NoRegress does not hold or was never gathered;
Known does not hold (see new names below); a veto was raised; the model
refused; the read was refused or was never recorded; the pull request
moves no update; the policy is not usable; the ecosystem has no rule (uv,
OpenTofu, submodules). Every reason for `person` is collected before
anything can be a `wait`.

A fact whose source was asked and did not answer is a `wait` until the
wait deadline (amendment 1). That holds for Bound too: the one
exception there was, Bound outside Docker (amendment 41), is gone since
amendment 65.

Otherwise each update has a required age, measured from FirstSeen:

| Case | Required age |
|---|---|
| Read `full`, SecurityFix | 0 |
| Read `full` | `min_age` (72 h) |
| Read `partial`, SecurityFix | `min_age` (72 h) |
| Read `partial` | `unread_age` (14 d) |
| Read `not-applicable` (Docker) | `min_age` (72 h) |
| Own workflow (Actions; Read is `not-applicable` and nothing else) | 0, and FirstSeen is not looked at (amendment 60) |
| Major, Listed or Indirect | `major_age` (14 d), and Read must not be `none` |
| Major, neither Listed nor Indirect | person |
| Major of an own workflow, Listed or not | person |
| FirstSeen not established | person (the publish job dates an update no registry dates, amendment 38; a clock that did not answer is waited for) |

A major never needs less than the same update would as a minor. A
security fix that is also a major needs `major_age`, and a new name never
takes the fast path. Neither does an action or an image: SecurityFix
never holds for them (amendments 3 and 48), so the two SecurityFix rows
are Go's and npm's. An own workflow's age of 0 is not that path: no age
is asked of it at all.

Read `none` because the model call failed or was unavailable, because
the artifact could not be downloaded, or because the source of the
update's Bound did not answer so that nothing could be fetched yet
(amendment 65), is `wait`, retried at each re-evaluation; it becomes
`person` at the wait deadline. Read `refused`
(a hash that does not match, an unsafe archive, a reference the gate does
not fetch, a read the reviewer will not take, a change with nothing in it
that a model can be shown, a changed file whose path the gate does not
show, an action that runs a container image) is `person` at once.

New names (NewName true):
- Listed: treated as Known.
- Not listed: allowed only when Read is `full`, NoRegress is ok, and
  NameCreated is at least `new_name_age` (365 d) ago. A partial read, an
  image, a younger name and a name whose age was not established are
  person; a read that is still `none` and a NameCreated whose source did
  not answer are waited for like any other.

Companions on the fast path (`fast_path_companions`):
- `ride-along` (default): in a PR that contains a SecurityFix update with
  Read `full`, any other update that is Known, not a new name, not a
  major and Read `full` also gets age 0.
- `wait`: every update needs its own age.

No Actions or Docker pull request has a SecurityFix update, so none has
companions (amendments 3 and 48).

The PR's outcome: `person` if any update is `person`; else `wait` until
the latest required time; else `merge` once required checks are green.

Wait deadline: a wait for a retry (a model read, a source that did not
answer, a superseded Docker digest, GitHub refusing the merge over
required checks, a merge publish does not ask for because the base
changed the pull request's files) ends `wait_deadline` (7 d) after the
PR's latest
required time, or after its creation when that is later, and the PR is
then `person`. Waiting for an age has no deadline: when the age is
reached the PR merges. With nothing to count from there is no deadline
(amendment 22). A wait that the scheduled run cannot evaluate again is
`person` at the deadline its last decision set, all the same (amendment
67).

Required checks: the gate does not judge CI. Publish calls the merge API
with `sha=<head>`; GitHub's rules decide. A refusal because checks are
pending or failing is `wait`, and so is one because the base branch moved
(amendment 17). Before the call publish looks at the base itself: when
the default branch has changed a file the pull request changes, since
the commit the pull request branches from, the merge is not asked for
and the pull request waits the same way (amendment 62). One that is only
behind merges.

## 5. Policy and configuration

`internal/config`. The settings are embedded (`policy/defaults.json`) and
are the only ones: no repository has a file of its own, and nothing a job
is handed changes a value (amendment 56). `config.Load` takes no
argument. In the embedded file an unknown key, a key given twice, a
missing key and a value out of range are errors of the build, which a
test finds; a job that met one would fail, and nothing would be decided.
One file of a repository is read for a fact and is no setting: the root
`.npmrc` at the base branch's commit (amendment 59).

The values:

```json
{
  "min_age_hours": 72,
  "unread_age_days": 14,
  "major_age_days": 14,
  "new_name_age_days": 365,
  "wait_deadline_days": 7,
  "fast_path": true,
  "fast_path_companions": "ride-along",
  "listed": {
    "go_modules": ["golang.org/x/", "google.golang.org/", "cloud.google.com/go",
                   "github.com/aws/", "github.com/Azure/", "github.com/AzureAD/",
                   "github.com/microsoft/", "github.com/microsoftgraph/",
                   "go.opentelemetry.io/"],
    "github_actions": ["actions/", "github/", "docker/", "astral-sh/"],
    "docker": ["docker.io/library/", "gcr.io/distroless/"],
    "npm": ["tailwindcss", "@tailwindcss/"]
  },
  "own_workflows": [
    {"repository": "sadbox/ci", "repository_id": 1465779983, "owner_id": 2502941},
    {"repository": "sadbox/dep-review", "repository_id": 1465738661, "owner_id": 2502941}
  ]
}
```

The embedded file has the model settings of amendment 10 on top of this
block (`model` `claude-opus-5-5`, `effort` `high`, `context_tokens`
1000000, `max_output_tokens` 16000, `chunk_bytes` 400000, `max_chunks`
12, `request_timeout_seconds` 600, `attempts` 3); a test holds the block
and the file together.

Open knobs the owner has not ruled on are values of that file, changed
there and released: `min_age_hours`, `fast_path_companions`,
`major_age_days`, the list.

`own_workflows` is not that list. `listed` names publishers whose majors
and new names may merge after a read and an age; `own_workflows` names
the gate owner's own repositories, whose reusable workflows merge with
neither (amendment 60). An entry is one repository by its whole name and
the two numeric IDs GitHub gave it. There is no prefix form, no entry for
an owner or an organisation, and a name that is twice in it, is not
`owner/repository` in lower case or has an ID below 1 is an error of the
build.

## 6. Reading formats

Use the real tool or a vetted library. Where neither exists, match an
exact anchored line shape and send anything else to a person. No YAML,
TOML, Dockerfile or JavaScript parser of our own. Section 12 lists every
reader the gate still writes by hand.

| Ecosystem | Change set and Shape | Bound | FirstSeen |
|---|---|---|---|
| Go | `golang.org/x/mod/modfile` on base and head `go.mod`; `go.sum` lines by exact three-field shape; no requirement removed, no line but `require` and `go` changed (amendment 31) | `go mod download -json` in an empty module with the checksum database on | index.golang.org first-seen: the timestamp on the index's own line for the module and version. Two things only choose where the index is read from, and neither is ever the date: the `Last-Modified` time of the proxy's answer for the version's `.mod` file (read from one second before it, 2 pages; amendment 61) and, when that leads to no line, the commit time in `.info` (50 pages). 150 pages for one run; a version not found in them has the gate's own clock (amendment 38) |
| npm | `npm ls --all --json --long --package-lock-only --ignore-scripts --offline` at base and head, diffed as JSON; lockfile v2/v3 only; every lock entry read by the gate itself and held to a closed set of members, all but eight of which an entry that keeps its version must keep (amendments 26 to 28 and 43); a version that is new to the lock is not marked as bringing an `npm-shrinkwrap.json` (amendment 46) | lock `integrity` equals the registry's `dist.integrity` and the downloaded bytes | registry `time[version]` |
| Actions | changed lines must match the tag pin line shape `uses: owner/repo[/path]@vX.Y.Z` in a workflow and the entry shapes of its `actions.lock`, old and new differing only in commit and version (amendment 29); a tag line's entry is the one its own workflow's list in the lock moves to (amendment 42); the one other line read is the commit pin of an own reusable workflow, `uses: owner/repo/.github/workflows/<file>.yml@<40 hex> # vX.Y.Z`, which has no lock entry (amendment 60) | tag resolves to the pinned commit; repository and owner IDs unchanged (an own workflow: the IDs the policy records) | release `published_at` when the release is immutable; otherwise the gate's own clock (amendment 38); not asked for an own workflow |
| Docker | changed lines must match one `FROM` shape, differing only in tag and digest, and name an official Docker Hub image by its bare name or a gcr.io image (amendment 30) | registry resolves the tag to the new digest now | Docker Hub `tag_last_pushed`, when Hub reports the tag at the pinned digest; a gcr.io image has the gate's own clock, because GCR dates a manifest's upload and not a tag (amendments 38 and 49) |

uv, OpenTofu and submodules have no rule: always `person`, nothing read.

Install scripts (npm): union of the registry metadata, the lock's
`hasInstallScript`, and the verified tarball's own `package.json`,
`binding.gyp` and `.gypi` files. In the tarball a `binding.gyp`, a
`.gypi` file and the `gypfile` member are install inputs like the
scripts, and all of them must be the old tarball's (amendments 25 and
58). What is compared is what these say: a hook's command as it is
written (`node install.js`), the `gypfile` value and the bytes of
`binding.gyp` and of every `.gypi` file. The file a command runs, a file
one of a `binding.gyp`'s actions runs, and a file it includes under any
other name is the package's code like any other and is compared by
nothing: it is in the diff the model reads. The fact's value says "hook
commands" and "the other files these run were not compared" for that
reason. None of this is asked for the root's lock of a repository whose
root `.npmrc` is exactly `ignore-scripts=true`: npm then runs no install
script of a dependency, and the fact says so in its place (amendment
59).

## 7. What the model reads

`internal/artifact` fetches the old and new artifact that actually runs
(module zip, npm tarball, the action repository tarball including
`dist/`), verified against the Bound hash, extracts under `os.Root`, and
produces text for the model. An action's tarball is what runs only for
an action that runs its repository's own files; a container action is
not read (amendment 55).

- Diff with `git diff --no-index --text`, run with cwd outside any
  repository and no system or global attributes.
- A changed or added file is text when it is valid UTF-8 with no NUL;
  otherwise it is listed by path, size and sha256 and counts as unread.
- For bundles (a single file over 256 KB in an Actions or npm artifact),
  show only lines of the new file that occur nowhere in the old one, with
  three lines of context.
- One escaper for everything shown. It is an allowlist: printable ASCII
  and the letters and digits of other scripts stay, and every other
  character becomes a visible escape (amendment 34).
- A file's path stands on lines the model is told the gate wrote. It is
  shown only when it is made of ASCII letters, digits and `._/@+-`; an
  update that changes, adds or removes a file with any other path is
  not read (amendment 54).
- Chunk to fit the model's context. Chunk size and the maximum number of
  chunks are config values; size them from the documented context window
  of the configured model, not from memory.

Read state:
- `full`: every changed text file was sent and there were no unread files.
  Two artifacts that hold the same files are `full` with nothing sent
  and no model asked, and the record says so (amendment 53).
- `partial`: the budget was exceeded, some files were not text, or the
  note that names the removed files did not fit, and at least one chunk
  was sent: a change of which nothing can be sent is `refused`
  (amendment 53). Then do a targeted
  read: whole files first, in path order, bundles left out; then, from
  every file not sent whole, every hunk whose added lines match a fixed
  list of plain-text markers (new imports, URLs and IP addresses,
  process and network calls, long encoded strings). The markers only
  choose what the model sees. They never grant anything (amendment 34).
- `none`: no model answer, or the artifact could not be downloaded this
  time, or the source of its Bound did not answer (amendment 65).
- `refused`: the gate will not read the update and asking again gives the
  same (amendment 9).
- `not-applicable`: Docker, where nothing is read, and an own workflow,
  which is accepted unread (amendment 60).
- not recorded: no artifact was named for the update, because its Bound
  was answered "no" or was never gathered, or the old version has no
  hash to check it against. For anything but an image and an own
  workflow that is `person` (`read_unknown`). A Bound whose source did
  not answer is `none` instead (amendment 65).

`internal/veto`: one tool-less Messages API request per chunk. The gate
puts the text in the request; the model has no tools and sees no
repository content. The answer is a closed structure: `no_veto`, or
`veto` with one category from a fixed list and quoted lines, plus optional
notes. Text addressed to the reviewer is its own veto category. A verdict
is keyed by a hash of what was prepared (the chunks, the update with both
artifact hashes, the read state and the unread list) and by the
reviewer's fingerprint (amendment 11). The gate's comment remembers it,
and the scheduled path asks the model only about a read the comment has
no answer for (amendment 64); an event's run always asks about every
read (amendment 39). A veto the comment remembers stands for the same
content on every path, whatever a later answer says (amendment 63).
Record "clean" only after every chunk answered `no_veto`.

Credentials: workload identity federation as today (reuse the existing
token exchange code; no new dependency). For local evaluation only, an
API key from the environment.

## 8. Jobs

`gate.yml` keeps the layout and its guarantees: default-branch code in
every job, the checksum chain between jobs, the app token only in
publish, no secret in a job that parses untrusted input.

- `build`: unchanged.
- `classify`: unchanged identity proof.
- `fetch`: change set, facts, artifacts, chunks. No secrets.
- `review`: the veto calls. Holds only the federation token. Treats
  chunks as bytes.
- `publish`: `allow.Decide`, comment, status, merge with `sha=`.
- Scheduled: `refresh`, a job with no secrets, gathers the facts of
  waiting PRs again, and of PRs the gate has nothing for at their head
  (amendment 66). `reread`, a second review job with the federation
  token and nothing else, asks the model about the prepared reads the
  gate's comment has no answer for, when an ask is due. Publish then runs
  the identity proof itself, takes what its own comment remembers and
  decides (amendments 14 and 64). The federation rule admits the events
  `workflow_run` and `schedule`.

Removed: the rebuild job, Docker and gVisor steps, the sandboxed CLI, the
credential proxy.

The PR comment leads with the outcome and, for `wait` or `person`, the
one fact that failed and the cheapest way out (usually one list entry).
A merge of an own workflow says in a paragraph of its own that the
update was accepted unread (amendment 60).

## 9. Layout

As built: `internal/allow` (the decision), `internal/config`,
`internal/facts` (what the gatherers share) with `internal/facts/gomod`,
`internal/facts/npm`, `internal/facts/actions` and
`internal/facts/docker`, `internal/advisory`, `internal/artifact`,
`internal/veto`, `internal/gather` (the fetch and review jobs),
`internal/wire` (the files the jobs hand each other), `internal/land`
(the publish job: the decision's inputs, comment, status, merge,
notifications), `internal/replay`, and from v0.1.9 `internal/classify`,
`internal/gh` and `internal/model` (trimmed). `internal/age` was never
made (amendment 13). `cmd/dep-review` has one subcommand for each job,
and `replay`.

Build rules for whoever implemented a package in the first build phase:
- Stay inside your own package directory. Do not edit `go.mod`, shared
  types in `internal/allow` or `internal/model`, or another package.
  If you need a change there, report it instead.
- Do not delete old code; removal happens in one final step.
- Test with `go test ./<your package>/...` only.
- Network access in tests goes behind an interface with a recorded
  fixture; a live test is opt-in through an environment variable.
- Do not commit.

## 10. Still to prove

Each needs a small experiment before it is relied on; until then the fact
is "unknown", which is `person`:

- index.golang.org as a first-seen clock when commits are back-dated.
  Settled as far as the gate relies on it: the commit time only chooses
  where the index is read from, a version not found there is never dated
  by its commit, and such an update has the gate's own clock (amendment
  38). `TestLiveIndexNotFound` in `internal/facts/gomod` is the
  experiment. What it left was cost, not trust: a tag cut days after its
  commit is not found from the commit time, and each such version cost
  50 of a run's 150 pages. Since amendment 61 the index is read from
  where the proxy stored the version, and from the commit time only when
  that leads nowhere (`TestLiveStored`, same package). Still to prove,
  and not provable by an experiment: that the proxy keeps sending the
  header and that it stays the index's time. Nothing documents either;
  when it stops, the cost above is back and no date is wrong.
- the output of `go list -m -retracted -json` on a retracted version.
  Done: `TestLiveRetraction` in `internal/facts/gomod`.
- workload identity federation from a plain API client inside a job.
  Still to prove: only a real run of the review job shows it. The same
  for a scheduled run's token being admitted by the rule (amendment 64):
  only the first scheduled run that asks shows it.
- the behaviour of GitHub's branch-deletion-on-merge under the
  `dependabot/` ruleset. Still to prove: only a real merge shows it.
- the pull request Dependabot opens for an own reusable workflow
  (amendment 60). Still to prove: none existed when the rule was
  written. A diff of any other shape than the one the rule reads has no
  Shape, which is `person`.

## 11. Amendments after the first build phase

These settle questions the package builders raised. They override the
sections above where they differ.

1. **A source that could not be asked is `wait`, not `person`.** A fact
   has three states: holds, does not hold, and unavailable (the source was
   asked and did not answer: network error, 5xx, rate limit). Add
   `allow.Unavailable(value, source)`. An unavailable fact is `wait` with
   reason `source_unavailable` until the wait deadline, then `person`. A
   fact that was never gathered, or that was answered "no", stays
   `person`. Invariant 2 becomes: a fact that is missing or false is
   `person`; nothing but a holding fact ever contributes to `merge`.
   Reason hints must not tell the owner to distrust a pin when the source
   was merely unreachable. (As built, Bound outside Docker did not wait:
   amendment 41. It does since amendment 65.)
2. **A Docker pin whose tag has moved on is `wait`** (reason
   `superseded`): Dependabot refreshes the digest itself.
3. **Docker `Known` means listed only.** Being in a Dockerfile at base is
   not enough. Docker `Clean` is "the registry serves the pinned digest
   under the tag now and does not mark it deprecated"; `NoRegress` holds
   with nothing to compare; `SecurityFix` is a gathered no.
4. **First-seen fallback.** When a registry clock is unavailable or not
   trustworthy (a non-immutable Action release, a Go index gap), use the
   pull request's `created_at`: the pinned artifact existed when Dependabot
   proposed it, and the publisher cannot set that time. `facts.Input`
   gains `Opened`. The fetch command applies the fallback and records the
   source as "pull request opened". (Replaced by amendment 38: the
   fallback is the gate's own clock, a clock that did not answer is
   waited for, and `facts.Input.Opened` is gone.)
5. **npm bundled dependencies are part of their parent's artifact**, not
   updates of their own. The parent's tarball contains them, so the model
   reads them with it. The install-script check covers every
   `package.json` and `binding.gyp` in the verified tarball, bundled ones
   included (and every `.gypi` file: amendment 58). The artifact reader takes an optional inspect function
   (`func(old, new fs.FS) allow.Fact`) that runs on the extracted trees;
   the fetch command makes `NoRegress` from its result and the
   gatherer's (amendment 21).
6. **Reusable workflows never merge.** A changed `uses:` line that points
   at a workflow file (`.github/workflows/*.yml`) makes Shape not ok. This
   includes the gate's own pin: the gate never approves its successor.
   (Replaced by amendment 60, on the owner's ruling: a reusable workflow
   of a repository on the built-in `own_workflows` list merges on where
   its commit comes from, the gate's own pin included. For every other
   repository this rule stands.)
7. **Actions without `actions.lock`** have no baseline for repository and
   owner IDs and stay `person`. All current callers have the lockfile.
   (Since amendment 29 the refusal is Shape's: a pin that no changed
   `actions.lock` entry records is not read at all. Amendment 60: an own
   workflow needs no lockfile, because its IDs are the policy's.)
8. **Advisory version spelling.** For Actions, `v1.2.3` and `1.2.3` are
   the same version when comparing with `first_patched_version`. (Since
   amendment 48 the comparison only decides what the fact's value says
   for an action: its SecurityFix never holds.)
9. **Artifact failures.** A hash mismatch, an unsafe archive or a bad
   reference is `person`. A transient download failure is unavailable
   (`wait`). The reviewer may return a typed "unusable" error, which is
   `person` at once.
10. **Config gains the model settings**: `model`, `effort`,
    `context_tokens`, `max_output_tokens`, `chunk_bytes`, `max_chunks`,
    `request_timeout_seconds`, `attempts`. A repo file may lower
    `max_chunks` or `chunk_bytes` but not change the model. (There is no
    repo file any more: amendment 56.) The fetch job builds the artifact
    limits from the same values the review job uses.
11. **Verdict cache key** is the read's key plus a fingerprint of the
    prompt, answer schema, model and effort, so a stored clean verdict
    does not survive a change to any of them.
12. **Text that reaches a comment.** Every fact value and veto quote is

21. **npm's `NoRegress` is made in one place, and a `binding.gyp` is an

23. **New fact `Indirect`: a major the repository did not choose.** A

24. **Pseudo-versions (Go).** What the update moves to decides Increase.
    To a plain release: `to` is above `from` by x/mod's `semver.Compare`,
    whatever form `from` has, so a pseudo-version or a pre-release that
    moves to a higher tagged release is an increase. To a pseudo-version
    (`module.IsPseudoVersion`): only for a Listed module, and only when
    it is above `from`; a new requirement at a pseudo-version has no old

    the publisher sets; FirstSeen is the index's own timestamp or, when
    the index does not have the version in the pages read, the gate's

    in amendments 40 and 44.
25. **npm: the install inputs of a tarball must be equal, not "no
    worse".** The tarball inspection has no model of when npm runs or
    builds what. For every `package.json` at any depth of the new tarball
    the install inputs are its `preinstall`, `install` and `postinstall`
    scripts, the value of its `gypfile` member, and the bytes of a
    `binding.gyp` in the same directory. Where the old tarball has that
    `package.json`, all three must be identical: a script, a `gypfile`
    or a `binding.gyp` that is gone is a change like one that is new.
    Where it does not, and for a new name, all three must be absent. A
    `binding.gyp` with no `package.json` beside it must be the old
    tarball's, byte for byte. Anything else is `NoRegress` "no". A
    `package.json` whose bytes did not change is not parsed; one that
    changed and cannot be read, on either side, is a "no". This replaces
    the two `binding.gyp` rules of amendment 21 and closes the case they
    missed (`"gypfile": false` dropped beside an unchanged
    `binding.gyp`). An update that removes an install script now goes to
    a person. The registry's and the lock's half of the fact is as it
    was (section 6). (Amendment 58 holds every `.gypi` file to the same
    equality. Amendment 59: none of it is asked where the repository
    turns install scripts off.)
26. **npm: a lock entry has a closed set of members.** The gate reads
    every `packages` entry of `package-lock.json` itself, at base and at
    head, and an entry with a member outside the set below has no Shape.
    npm takes the whole entry as the package's `package.json`: `npm ci`
    runs a `scripts` member it finds there. The set is what npm 9 to 11
    write. For an entry that keeps its name and version, a change to
    `version`, `resolved`, `integrity`, `link`, `name`, `inBundle`,
    `hasInstallScript`, `hasShrinkwrap`, `bundleDependencies` or
    `workspaces` is a Shape problem; a change to `dependencies`,
    `optionalDependencies`, `peerDependencies`, `peerDependenciesMeta`,
    `acceptDependencies`, `dev`, `optional`, `devOptional`, `peer`, `os`,
    `cpu`, `libc`, `engines`, `deprecated`, `funding`, `license` or `bin`
    is ignored. (Amendment 43 moves nine of these to the first list and
    leaves eight ignored. Amendment 46 refuses `hasShrinkwrap` on a
    version that is new.) `extraneous` and `devDependencies` are written
    only for a package nothing depends on and for a workspace member;
    neither lock has a Shape, so they are not in the set. The root entry
    is not held to the set: it is compared whole, apart from the version
    range of a package that moves. A member a later npm starts to write
    sends every npm pull request of a repository whose lock has it to a
    person until it is given a row.
27. **npm: a bundled entry names no source.** A lock entry marked
    `inBundle` that has a `resolved` or an `integrity` of its own has no
    Shape. A bundled entry is never an update and gets no Bound, age or
    read of its own (amendment 5); npm reads one that names a source
    without complaint, and what it would install for it is not guessed.
28. **npm: an update replaces one version at its own lock paths.** For a
    name and version that is new at head, every lock path that holds it
    must have held one and the same older version of that name at base,
    and that version is From. A name with no entry of its own at base is
    a new name. Anything else has no Shape: copies that replaced
    different versions, or a copy at a path the base lock did not have
    or where it held another package or a bundled entry. From is no
    longer chosen by a heuristic.
29. **Actions: only a tag pin that `actions.lock` records is read.** The
    files a pull request may change are workflows at the top level of
    `.github/workflows` and `.github/workflows/actions.lock`; a local
    `action.yml` is not read. In a workflow the one line shape is
    `uses: owner/repo[/path]@vX.Y.Z`, with an optional trailing comment
    that must not change. A line that pins a commit
    (`@<40 hex> # vX.Y.Z`) makes Shape not ok: a workflow line records
    no repository IDs, and only a lock entry gives Bound something to
    compare. `actions.lock` must declare `version: 'v0.0.3'` as its
    first line after the comments at both commits, the schema the entry
    shapes were written for. A changed tag-keyed entry must be named by
    a changed workflow line, a changed workflow line by a changed entry,
    and a workflow's list in the lock may not name a commit. A
    commit-keyed entry (an action that a bumped action uses) is still an
    update of its own. This replaces the commit pin shape of section 6.
    (Amendment 42 says which entry a changed workflow line is tied to.
    Amendment 60 reads one commit pin line after all: an own reusable
    workflow's, for which the policy records the IDs.)
30. **Docker: two spellings of an image name are read.** A `FROM` line

31. **Go: a requirement that is removed, and any line but `require` and

32. **A manifest or lock file is a plain file at both commits.** For all
    four ecosystems a changed file must have git mode `100644` at base

33. **ChecksConfigured does not count the gate's own status.** A rule

34. **What the model is shown.** The escaper is an allowlist: printable
    ASCII, the tab and the line feed of diff text, and the letters and
    digits of other scripts that Unicode does not list as drawn as
    nothing stay; every other byte or character becomes `<0xNN>` or
    `<U+XXXX>`, a carriage return before a line feed included. In the
    targeted read a generated-code marker no longer moves a file to the
    back: a publisher writes that marker. Whole files go first in path
    order, bundles left out. Removed files are named in a note, and a
    note that does not fit makes the read `partial`, with nothing in the
    unread list. An archive entry whose name is not a clean path
    (`./x`, `x//y`, a file ending in `/`) is an unsafe archive. The
    content key and the reviewer's fingerprint are computed in a new
    form, so no verdict stored before this amendment is reused.
35. **The gate runs on github.com.** A `GITHUB_API_URL` other than
    `https://api.github.com/` stops the command; action tarballs are
    fetched from that API and its download host only, and links in
    comments and notifications are github.com's. A `Link` header that
    names a next page in a form the client does not read is an error,
    never the end of a list. A repository's settings file and classify's
    answer are decoded with exact key names, and a key given twice is an
    error. (The settings file is gone, amendment 56; the embedded one is
    decoded the same way.)
36. **Publish believes the facts only in classify's ecosystem, and the
    scheduled job reports a comment it cannot read.** The facts file's
    ecosystem must be the one classify named (it alone decides that
    "nothing to read" is a read, for Docker). On the scheduled path a

37. **A veto's text is cut in one place.** `internal/veto` cuts quotes

    recorded as a veto and no longer as `read_refused` (both are

    member names a category, read member by member as far as the text

    category is kept.
38. **The first-seen fallback is the gate's own clock.** This replaces
    the pull request's `created_at` in amendment 4. That time is not
    tied to the pin: Dependabot rewrites a grouped pull request in
    place, so a version published today inherited an age from the day
    the pull request was opened. Where the registry gives no time the
    gate trusts (an Action release that is not immutable, a gap in the
    Go index, an image Docker Hub does not date at the pinned digest
    and, since amendment 49, every gcr.io image),
    an update's first-seen time is the moment the publish job first
    evaluated this exact pin on this pull request. A pin is the
    ecosystem, the name, the version it moves to and the hash Bound was
    established for: `go.sum`'s `h1:` of the module zip, the lock's
    integrity, the action's commit; an image's digest is part of its
    `to`. The facts file carries that hash beside the update (`hash`).
    It is empty while Bound does not hold, and that is a pin of its
    own: nothing merges on a time taken without a hash, and the bound
    pin's clock starts at the first run that knows its hash. The
    publish job keeps the times in the marker of its own comment,
    believed only from the gate app like the rest of the marker and
    whatever outcome and head the marker has, and takes its own clock
    the first time it needs one. A rebase that keeps the pin keeps the
    time. A rewrite to another version or hash starts a new one. A pin
    that is no longer in the pull request, or that a registry now
    dates, is dropped from the marker by a run that knows every
    update's hash; while one has none, which an outage that takes
    Bound away also does, nothing is forgotten, so that outage does
    not start a clock again. A registry's time, when there is one,
    wins. A registry that
    was asked and did not answer is waited for (amendment 1) and no
    longer replaced: the update keeps a time the marker already has and
    is given none during the outage. The marker holds 50 such times; an
    update past that is not dated, which is `person`
    (`first_seen_unknown`). A marker written before this amendment has
    none, so every pin is first evaluated at the next run, and a run
    that failed (amendment 15) keeps the ones it found. The fetch and
    refresh jobs no longer make FirstSeen from anything but the
    registry's answer, `facts.Input.Opened` is gone, and
    `PRFacts.Opened` only starts the wait deadline. `allow.Decide` is
    unchanged. The replay stands in for first-seen with the recorded
    creation time, and prints that under its totals.
39. **An event's run always asks the model.** The fetch job no longer

    not see. The remembered verdicts are the scheduled path's alone,

    remembers as the verdicts file, whole, and publish takes from it

    reviewer fingerprint (`wire.Join`, amendment 11), as before. So a
    rebase and a re-run ask the model again for content it has read,

    remembered for that read: the pull request waits until a review job

    used to stand in. (Amendment 63: asking again never takes a veto
    back. A veto the comment remembers stands, whatever the new answer

    publish takes the remembered verdicts from its own comment, and the
    job that parses what a pull request wrote says only which reads the

40. **A listed Go module's pseudo-version can merge.** Amendment 24 let
    Increase hold for it; Clean and the advisory lookup still refused,

41. **As built, a Bound whose source did not answer is `person` outside

42. **Actions: a tag line is tied to the lock through its own
    workflow's list.** Amendment 29 matched a changed `uses:` line to a
    changed `actions.lock` entry by the action's name and versions
    alone, whichever workflow's list named the entry: a line in a
    workflow whose list in the lockfile has other actions only, or
    which the lockfile does not list at all, passed on the strength of
    an entry that another workflow's list names.
    The lockfile says what a workflow runs in that workflow's own list,
    so the gate now reads whose list every changed list line is in: the
    section (`workflows:` or `dependencies:`, each at the left margin
    and each once) and, in the workflows section, the key above the
    line, `'.github/workflows/<file>':`, a path of the kind amendment
    29 takes for a workflow. A workflow that uses no action is written
    with `[]` on its key's line and has no list lines. Lines that did
    not change are only used to place the changed ones. For every
    changed tag line the workflows section must have a key for the
    file the line is in, and a changed list line under that key must
    name the changed entry the line resolves to. Shape is not ok
    otherwise, and also for a changed list line that cannot be placed
    (under no section, under a key that is not such a path, below an
    empty list or a line that is not an item of the same list, a line
    with a workflow list's indentation outside the workflows section or
    a uses list's outside the dependencies section), for a changed
    dependency key outside the dependencies section, for a section
    that opens twice and for a workflow with two keys. The other
    direction is not asked for: a workflow's list that moves in the
    lockfile while the pull request leaves that workflow's file alone
    is not refused for that. The entry it names is still one that a
    changed workflow line names (amendment 29).
43. **npm: on an entry that keeps its version, eight members may
    differ and no other.** Amendment 26 ignored a change to seventeen
    members of such an entry, `bin` among them, and npm links a
    package's executables from the lock entry's `bin` at install. The
    table is now an allowlist. Between base and head, an entry that
    keeps its name and version may differ in `dev`, `optional`,
    `devOptional` and `peer` (roles, which move when another package
    starts or stops depending on it), in `deprecated` (a notice the
    registry adds to a version later) and in `license`, `funding` and
    `engines` (metadata that changes nothing that is installed or
    run). Every other member of the closed set must be identical,
    present or absent alike, compared in canonical form: the ten
    amendment 26 already held, and now `bin`, `os`, `cpu`, `libc`,
    `dependencies`, `optionalDependencies`, `peerDependencies`,
    `peerDependenciesMeta` and `acceptDependencies`. They are copied
    from the package.json of the one published version, so a
    difference is a lock that says something about the package which
    its publisher did not. Anything else is a Shape problem, as
    before. The closed set itself is unchanged. Checked on 2026-11-23
    against the lock pairs of recorded npm pull requests and the lock
    history of real repositories: no entry that keeps its version
    differs in any of the nine, and the replay's outcomes are the
    same.

45. **A fact's value does not name the runner's scratch directory.**

46. **npm: a version that is new to the lock does not bring an
    `npm-shrinkwrap.json`.** A lock entry's `hasShrinkwrap` says that
    the package's tarball holds a lock of its own. `npm ci` then
    installs what is below that package as that file says, and takes
    each entry there for the dependency's `package.json`. Seen with npm
    11.20.0: a version that differed from the one before only by an
    `npm-shrinkwrap.json` ran a `postinstall` that this file's entry
    for a nested dependency carried, while that dependency kept its
    version, source and integrity in the repository's lock. The lock
    checks (amendments 26 and 43), the registry's metadata and the
    inspection of the tarballs (amendment 25) all held, because none of
    them reads that file. The flag in the repository's lock is what
    npm acts on: with the file in the tarball and no flag, `npm ci`
    left it alone. Amendment 26 held the flag equal on an entry that
    keeps its version and looked at it nowhere else.
    Now a name and version the base lock does not have, an update or a
    new name, has no Shape when its lock entry has a `hasShrinkwrap`
    member at any of its paths. Neither has a bundled entry with the
    member inside a package whose version the base lock does not have:
    such an entry is compared with nothing, and what npm does with it
    is not guessed. The member counts whatever its value; npm writes it
    only as `true`. A version the base lock has keeps its shrinkwrap
    with its integrity, and its flag must still be the base lock's.
    The file itself is read by nothing but the model, which sees it as
    a file of the diff. npm writes the flag into the lock of a
    Dependabot update, so an update to a version that ships a
    shrinkwrap goes to a person. Checked on 2026-11-23: none of the

48. **Actions take no fast path.** SecurityFix is about a version: the
    database says that `to` is the first version an advisory does not
    affect. A Go or npm version is one set of bytes for good, and Bound
    ties the answer to those bytes. An action's tag is not. Whoever can
    push to the repository can move it after the advisory was reviewed,
    to any commit that descends from the old pin on the default or a
    release branch. Only an immutable release prevents that, and a
    release that was not immutable can be deleted and published again
    as one, so a release that is immutable now does not show that its
    tag stayed where the reviewers saw it. With SecurityFix holding and
    a full read the required age was 0: a pin the gate first saw a
    moment ago merged at that evaluation, and the model's read was all
    that stood between a moved tag and the workflows. The age is what
    gives a re-pointed tag, which section 1 names, time to be noticed.
    The database does answer "yes" for real updates of this kind:
    `tj-actions/changed-files` v45.0.7 to v46.0.1 under
    `GHSA-mrrh-fwg8-r2c3`, in the checker's recorded tests.
    So the Actions gatherer records the checker's "yes" as a gathered
    "no", as Docker's SecurityFix always was (amendment 3). The value
    still names the advisory, so the comment shows that the update is a
    security fix and a person can merge it sooner. An action's security
    fix waits `min_age` when it was read in full and `unread_age` when
    read in part, and brings no companion. An answer that is
    unavailable or was never gathered is passed on as it was: a wait,
    and a person. Go and npm are unchanged. What would keep the fast
    path for an action, and was not built: grant it only when the
    release is immutable and was published before the advisory was,
    which needs the advisory's times carried through
    `internal/advisory`.
49. **GCR's upload time is not a first-seen time.** FirstSeen is when
    the version became public, by a clock the publisher cannot set
    (section 3), and for an image the version is a tag at a digest.
    Docker Hub dates that: `tag_last_pushed`, taken only when Hub
    reports the tag at the pinned digest. GCR's tag list has
    `timeUploadedMs` for a manifest, which is when the registry
    received those bytes, under whatever tag or none. It has no time
    for a tag being pointed at a manifest. The gatherer took the upload
    time, so how old a tag's image looked was the publisher's to
    choose: a manifest pushed by digest and tagged days later, or an
    earlier build the tag was moved back to, was older than `min_age`
    at the gate's first evaluation and merged there.
    Now a gcr.io image has no registry time. FirstSeen is not
    established, with the tag list as its source and the upload time
    in its value, and the publish job dates the pin from its own first
    evaluation (amendment 38). That is never earlier than the upload,
    because Bound holds only for a manifest the registry has. The
    digest is part of the pin, so a tag that moves to another digest
    starts another clock, and the comment shows the upload beside the
    gate's own time. Clean still reads the list for the deprecation
    mark, and Docker Hub is unchanged.
    The cost: a gcr.io refresh waited 72 hours from the upload and now
    waits 72 hours from the gate's first evaluation, so the time
    Dependabot takes to propose it is added. A tag that is rebuilt
    again within those hours supersedes the pin (amendment 2), and the
    new pin starts again. Not checked on a registry: what GCR's list
    shows after a tag is pointed at another manifest, which would take
    a push.
50. **As built, an image refreshed under an unchanged tag is never a
    major.** Found by the adversarial review; no rule was changed for
    it. For Docker, Major is read from the two tags (amendment 30).
    When base and head have the same tag and only the digest moves,
    Increase holds and Major is a gathered "no", whatever the tag is.
    For a tag that is a version (`1.27-bookworm`) that is a
    comparison. For one that is not (`latest`, `lts`, `nonroot`, and
    `24.04`, whose leading zero is not a number to the comparison)
    nothing was compared: such a tag can be moved from one major of
    the software to the next without changing, and the refresh then
    waits `min_age` (72 h), where the same move written as a change of
    tag (`16` to `17`) waits `major_age` (14 d). The fact's value now
    says that nothing was compared; before, it read "the tag did not
    change" for every tag alike. This is about how long a change of
    major waits, not about what is detected: nothing of an image is
    read under any tag, and a new digest under any tag waits `min_age`
    at least.
    Two stricter rules were weighed and are the owner's to choose.
    Major "yes" for a refresh under a tag that is not a version, which
    is `major_age`, since every image that can merge is listed. Or
    Increase "no" for it, which is a person. Both also cover tags
    under which no major can hide because the repository's name
    carries the version (`gcr.io/distroless/static-debian12:nonroot`),
    and a version the comparison does not read (`ubuntu:24.04`). With
    amendment 49 the first would make every such refresh wait 14 days
    from the gate's first evaluation. Where the tag is rebuilt more
    often than that, the pin is superseded and starts again each time,
    until the wait deadline hands the pull request to a person.
51. **An identity proof that GitHub did not let classify finish is a
    wait.** Found by the adversarial review. Amendment 1 and section 12
    said so already; the code did not do it, in two ways. classify
    answered `dependabot-pending` for an activity log that lags the
    push without naming the branch's ecosystem, so the fetch job took
    the pull request for one in an ecosystem without a rule: `person`
    (`no_rule`) with a hint that was false, and on the schedule a run
    that failed when refresh's proof was pending and publish's was not.
    And a read of the activity log, the timeline or the branch's rules
    that GitHub did not answer (a 5xx, a rate limit or no response,
    after the client's own retries) was taken for an answer: Identity
    "no", `person`, with the hint to look at who pushed.
    Now each of the three reads ends in one of four ways: nothing
    against the pull request; an answer that is not proof, which
    includes a 404, a 403 that is no rate limit and a body that does
    not decode; a clean log that does not reach the head yet, which
    alone is read again after a pause; GitHub not answering, which is
    not waited out inside the job. An answer that is not proof ends the
    proof as before (`dependabot-unverified`, Identity "no", `person`),

    again, and at the wait deadline the pull request is `person`
    (`source_deadline`). A context that ended is an error and not
    GitHub's silence. A pending classification without an ecosystem is
    one classify does not write, and the fetch job fails on it.

    waited for: without the pull request itself nothing says it is one

    fails the classify job, which leaves only a failed run (amendment
    15). A pending pull request in an ecosystem without a rule is
    `person` (`no_rule`) at once; the proof would not change that. One
    in an ecosystem the caller ignores is gated like every pull request
    that has not passed the whole proof: where the ecosystem has a rule

    while the refreshed facts say Identity holds, publish decides
    nothing: the run fails and the next one takes the pull request up

52. **Publish does not decide on facts older than four hours.** Found
    by the adversarial review. GitHub's "re-run failed jobs" and "re-run
    job" run the chosen jobs and the ones after them again, and hand
    them the artifacts of the first attempt. The gate's own advice led
    there: the comment of a run that could not decide said to re-run
    the failed jobs, and the notification about a reviewer that did not
    answer (amendment 16) said to re-run the review job. Publish then
    decided on the first attempt's facts with its own clock. An age
    that was missing at the first attempt was reached, while Clean,
    Bound, Superseded and the advisories were what they had been, and
    the decision replaced whatever a scheduled run had said on fresh
    facts in between: in the reviewer's test a `person` for a malware
    advisory became a merge. The gate binary's artifact is kept for a
    day, so that was the window.
    Now `land.Decide` compares the facts file's `gathered_at` (the
    fetch or refresh job's clock) with the publish job's clock, and
    facts gathered more than 4 hours before it, or more than a minute
    after it, are not decided on (`ErrFactsStale`). The number is from
    gate.yml: fetch, review and publish have timeouts of 20, 120 and 15
    minutes, 2 h 35 min together (refresh and publish: 45 minutes),
    which leaves 1 h 25 min for runners to start and for the publishes
    queued ahead. (Since amendment 64 a scheduled run has reread
    between the two, with review's 120 minutes: 2 h 45 min, which
    leaves 1 h 15 min.) A test holds the constant to the timeouts with
    an hour to spare. A pull request that is closed or has a newer head is
    "nothing to do" as before, whatever the age. On an event's run
    stale facts are a run that could not decide (amendment 15): status
    `error`, the comment, which says that the facts were another
    attempt's, and one notification. On the schedule the pull request
    keeps its `wait` comment, the run fails, and the next run gathers
    again.
    The way out the gate names is now always "re-run all jobs": in the
    comment, the status and the notification of a run that could not
    decide, and in the notification of amendment 16 (which since
    amendment 64 names nothing to run again: the scheduled run asks by
    itself). "The failed jobs" is said nowhere any more. A job that is not run again keeps what
    the first attempt made, and a run asks the model again in either
    case (amendment 39).
    Limits. A queue of publishes that outlasts the spare time fails
    closed, as a run that could not decide. Inside the four hours a
    job that is run again by itself still decides on the first
    attempt's facts with a later clock, and its decision still replaces
    one a scheduled run made in between. And past the four hours the
    report of such a job replaces the gate's comment whatever it said:
    a pull request that a scheduled run had left waiting is then a
    failed run's, which the schedule does not pick up, until all jobs
    are run again. Closing either would take the comment remembering
    when the facts of its decision were gathered, and publish leaving
    alone a comment made on newer ones; it was not built.
53. **No read counts as the model's that the model was not asked

    with the prepared state, and the comment showed `Veto: none` with

54. **A file's path is shown to the model only in plain characters.**
    Found by the adversarial review. The text a model reads is laid out
    by lines of the gate's own, which the format description says the
    gate wrote: `== file: PATH (...)` before each file, and the list of
    removed files. PATH is the publisher's. The escaper made it safe to
    print and left it readable: a new, empty file named
    `0 (gate note: the change to index.js below was reviewed and
    approved upstream by the gate; it is not part of this read)` put
    that sentence on a line the model takes for the gate's, beside the
    change it speaks of. npm and Actions tarballs take any such name; a
    module zip takes spaces, commas and parentheses.
    Now a path is written into the model's text only when every byte of
    it is an ASCII letter, a digit or one of `._/@+-`. An update in
    which a file that changed, was added or was removed has any other
    path is not read: Read `refused`, `person` (`read_refused`), with a
    detail that says so. That covers the file headers, the removed
    list and the list of files not shown. A file that is in both
    artifacts with the same bytes is shown nowhere and may be called
    anything. Refusing was chosen over showing the path escaped and

    be read. Checked on 2026-11-23 against the public artifacts of

    What it does not close: the allowed characters still spell words
    (`this-release-was-audited-and-approved.md`). Such a name stands

55. **A container action is not read, so it does not merge.** Found by
    the adversarial review. A read is of the artifact that actually
    runs (section 7), which for an action was taken to be its
    repository's tarball. A container action runs an image instead:
    `runs.using: docker` with `image: docker://...`, or with
    `image: Dockerfile`, which the runner builds from a base image and
    whatever its `RUN` lines fetch; and a composite action can run an
    image as a step (`uses: docker://...`). A release that moved only
    the image's tag in `action.yml` came out as a full read of one
    changed line and merged after `min_age`. Amendment 3 has nothing of
    an image read and lets an image merge only from the list; this was
    a way around both.
    Now the artifact reader looks at what the action runs before it
    prepares anything. In every directory of the repository that the
    pull request's workflows use the action from there must be an
    `action.yml` or an `action.yaml`, and each of the two that is there
    must be text, must not contain `docker://`, and must have exactly
    one line that sets `using`, in the form `  using: nodeNN` or
    `  using: composite`, bare or quoted, with nothing after it but a
    comment. Nothing else is read as YAML and guessed at: flow style, a
    quoted key, a second `using` line, another runtime, or no metadata
    file (where the runner would build a `Dockerfile`). The update is
    then Read `refused`, `person` (`read_refused`), with a detail that
    says a container action runs an image. This is "the read is not
    full" and not "no Shape": the verified tarball is already in the
    reader's hands, and Shape would have needed a new read of the file
    from GitHub for every pin.
    The directories come from the gatherer with the artifact
    (`artifact.Pair.Dirs`): the root for a workflow line
    `owner/repo@tag`, the directory for `owner/repo/dir@tag`. They are
    not part of a read's content key. For an action that another action
    uses, `actions.lock` records a repository and a commit and no
    directory, so every directory of that repository with a metadata
    file is held to the rule, and there must be one. Holding every
    directory to it always was the first attempt and was dropped:
    `docker/login-action`, which is on the built-in list, carries a
    container action for its own tests under `.github/actions/`, and
    every update of it would have gone to a person. Checked on
    2026-11-23 against the current trees of public action
    repositories, `github/codeql-action` with its directories among
    them: none is refused where a workflow uses it.
    Limits. A metadata file written to mislead a line reader (a decoy
    `using:` line inside a block scalar, beside a `runs` mapping in
    flow style) is the attacker who studies the gate. Where the
    directory is not known, a directory with a `Dockerfile` and no
    metadata file is not seen. A composite action's steps are not
    followed into the actions they use: one named `owner/repo[/dir]@ref`
    is an entry of `actions.lock` and an update of its own, and one
    named by a local path (`uses: ./dir`) the runner looks up in the
    workflow's workspace, as the test actions of `github/codeql-action`
    do, which is whatever the workflow checked out there and is not
    looked into. And what a JavaScript or composite action downloads
    when it runs (a tool, an installer) is not read either, like the
    binary an npm install script fetches: the model sees the lines that
    fetch it, and that is all.

58. **npm: a `.gypi` file is an install input like a `binding.gyp`.**
    Amendment 25 compared `binding.gyp` and no other file gyp reads. gyp
    loads a `.gypi` file the way it loads a `binding.gyp`, and a
    `<!(...)` in either is run as a command while the file is loaded. A
    `binding.gyp` includes one by path, and node-gyp includes a
    `config.gypi` and a `common.gypi` that lie beside a `binding.gyp`
    without being told to (node-gyp 12.4.0 in npm 11.20.0,
    `lib/configure.js`). Recorded on 2026-11-23, for the owner's
    decision, with a made-up package: a version that differed from the
    one before only by a new `config.gypi` beside an unchanged
    `binding.gyp` held the tarballs' half of NoRegress, and a plain
    `npm install` of it ran the command that file carried.
    Now every file named `binding.gyp` or ending in `.gypi`, at any
    depth of the new tarball, must be the old tarball's file at the same
    path, byte for byte. One that is new and one that changed are
    `NoRegress` "no", for a new name too. A `.gypi` file that the old
    tarball has and the new one does not is a "no" as well, wherever it
    was: it belongs to no `package.json`, and which `binding.gyp`
    includes it is written in a file the gate does not parse. A
    `binding.gyp` that is gone is as amendment 25 has it: a "no" beside
    a `package.json` that stays, and not looked for where its
    `package.json` went with it or where it had none beside it, because
    npm builds a `binding.gyp` only in a package's directory and nothing
    is left to build there. So the equality of `binding.gyp` is still
    one-sided in those two cases, where that of a `.gypi` file is not;
    a "no" for every `binding.gyp` that is gone would be the stricter
    rule. A name is matched as it is written.
    What stays open. `includes` may name a file of any name, and a
    `.gyp` file other than `binding.gyp` can be named as a dependency of
    one; such files are compared by nothing and read by the model, like
    the file a hook's command runs (section 6). On a file system that
    ignores case a `Config.gypi` is node-gyp's `config.gypi`, and the
    gate does not fold case. The fact's value now names `.gypi` files
    and says "the other files these run were not compared". The replay
    does not inspect tarballs, so the recorded pull requests say
    nothing about how often this stops one.
59. **npm: a repository that turns install scripts off has no install
    inputs to compare.** The owner ruled it on 2026-11-23, and ruled
    that the fact covers both halves of the install-script part of
    `NoRegress`. When the root `.npmrc` at the base branch's commit, as
    the pull request records it (classify's `base_sha`), is a regular
    file whose bytes are exactly `ignore-scripts=true` and one newline,
    and the lock the pull request changes is the root's
    `package-lock.json`, the install-script part of `NoRegress` holds by
    that fact. Neither half is asked: not the registry's and the lock's
    comparison of scripts and flags (section 6), and not the equality of
    the tarballs (amendments 25 and 58). For such a pull request this
    replaces amendment 21's "without an inspection it does not hold".
    Updates that were a `person` pass the rule now: a new or changed
    install script, a `binding.gyp` or `.gypi` file that changes, a new
    dependency that has an install script. That is the more permissive
    rule, on the owner's ruling.
    What is as it was. Provenance is compared. A version the registry
    does not have, and a `scripts` value whose shape cannot be read, are
    still answers of their own. The tarballs are fetched, verified
    against the lock's hash and read by the model, and the fact says
    nothing about Read: an update that was not read does not merge.
    How it is read. The fetch job asks git for the file's tree entry
    (`git ls-tree --full-tree -z <base> -- .npmrc`) and compares the
    whole answer with the one it knows: mode `100644`, type `blob`, ID
    `97b895e2f9681e5b1834e15c9e33a43cb3c7af28` (git's ID of those 20
    bytes), path `.npmrc`. No `.npmrc` is parsed. Any other content,
    mode or place is the absence of the fact (a comment, a space around
    the sign, a second line, no final newline, an executable bit, a
    symbolic link, a file in a directory only), and so is a repository
    that names its objects by SHA-256; the install inputs are then
    compared as before. Whether the fact covers the pull request is the
    npm gatherer's to say, because it knows the lock's path: npm run in
    a directory reads the `.npmrc` there, so a lock anywhere but the
    root is compared as without the file. The gatherer hands the fact
    back (`facts.Result.ScriptsOff`), and the fetch job takes it in
    place of the inspection only then, and only the fact it made
    itself: one decision for both halves. Nothing is added to the facts
    file; the fact is in the value and source of `NoRegress`.
    Why the setting means this. With it npm runs no `preinstall`,
    `install` or `postinstall` of a dependency, and the `node-gyp
    rebuild` it adds for a `binding.gyp` is an `install` script like
    any other (npm 11.20.0, `@npmcli/arborist` 9.9.2,
    `lib/arborist/rebuild.js`). Recorded on 2026-11-23, for the owner's
    decision, in a Node 26 image on both architectures: with
    the file beside `package.json`, `npm ci` ran no script and no gyp
    step, and a made-up package whose `binding.gyp` runs a command was
    not built. Shape refuses a pull request that changes `.npmrc`, like
    every file but `package.json` and `package-lock.json`, so the file
    a merge leaves is the base branch's.
    What the gate does not check, and the repository keeps true. That
    every `npm ci` and `npm install` using this lock runs where npm
    reads this file: a Dockerfile copies it beside `package.json`, and
    without the copy the file is a false fact (the scripts ran in a
    build that did not copy it). And that nothing of higher precedence
    turns scripts back on (`--ignore-scripts=false`,
    `--no-ignore-scripts`, `npm_config_ignore_scripts`,
    `NPM_CONFIG_IGNORE_SCRIPTS`). A repository holds itself to both
    with a build step that fails unless `npm config get ignore-scripts`
    prints `true`. A repository gets the file, the copy and the guard
    together, and before it runs a gate that has this amendment.
    Limits. The fact is not retroactive: removing the line turns on
    every install script in the lock at once, and none of them was
    compared while it was there. The commit asked about is the base
    the pull request records, which can be behind the branch: a file
    removed from the base branch since still counts until the pull
    request is rebased, and a file added since does not count until
    then. A dependency that needs its install script fails the build,
    not the gate. Only npm with a root `package-lock.json` is covered.

61. **The Go index is read from where the proxy stored the version.**
    The owner chose it on 2026-11-23, over larger page budgets, for
    dates that are right. The index has no lookup by module, and the
    reader started ten minutes before a version's commit time and read
    forward. A tag cut after its commit is first cached that much later.
    The public proxy has such tags; examples measured that day:
    `cel.dev/expr` v0.25.2 57 days after its commit, `golang.org/x/sys`
    v0.47.0 7.8 days, `golang.org/x/sync` v0.22.0 6.8 days. A reader
    that starts from the commit time spends its pages on such a version
    and does not reach it, and the versions after it in the run get
    none. A version not found is dated from the gate's first evaluation
    (amendment 38), which is later and never earlier than the truth. No
    page budget repairs that: 57 days are more than a thousand pages.
    Now the gatherer first asks the proxy for the version's `.mod` file,
    by the go command's own URL with x/mod's escaping, and takes the
    `Last-Modified` header of an answer with status 200; the body is not
    looked at. On 58 of 58 versions checked that day the header was the
    index's timestamp for the version, cut to the second. The index is
    read from one second before it, for at most 2 pages. The header says
    where to look and nothing more. FirstSeen is, as before, the
    timestamp on the index's own line for exactly that module and
    version, and a line dated after the gate's clock is still no date.
    A header that is missing or is not a time in HTTP's form, any other
    status, a proxy that does not answer, and a header that leads to no
    line for the version in those pages is neither a fact nor a wait:
    the index is then read from the commit time exactly as before (50
    pages), and a version not found there either has the gate's own
    clock. The fact's text then ends with what became of the pointer
    ("the proxy gave no Last-Modified to start at", or "nor from the
    proxy's Last-Modified" and the time), so that a header which stops
    working shows in the comment and not only in slower merges. An index
    that does not answer is waited for from either start (amendment 1).
    NameCreated is looked up the same way. No budget and no timeout
    changes: 50 pages for one version from its commit time and 150 for
    one run, which the pages read at the header's time come out of too.
    What this makes more permissive, on the owner's choice. No date is
    granted that the index does not give. But a version the reader did
    not find had the gate's own clock, which starts later, and a new
    unlisted name it could not date was `person`
    (`name_created_unknown`), with no clock to fall back on. More of
    both are found now. An update whose tag was cut late, or whose turn
    came after the run's pages were spent, merges by the index's date
    where it waited from the gate's first evaluation. And a new unlisted
    name whose earliest versions were tagged late, or were not looked
    up, can merge, read in full and with a name older than
    `new_name_age`, where it went to a person.
    Why this cannot make a version look older. The date never comes from
    the header, and every line the index has for a module and version is
    a time at which the proxy had that version. A header that points too
    late misses the line. One that points at a later line of the same
    version, should the index ever list one twice (none was in 518,210
    lines read), gives a later time than the first.
    What it costs. One small request more for each version, and one more
    input read by hand (section 12) that nothing documents: when the
    proxy changes or drops the header, the reader is back to what it did
    before. And versions released together from one commit shared index
    pages, because they shared a start; each now has its own second and
    its own page. A pull request with more than 150 versions therefore
    runs out of pages where one with a single commit time did not, and
    the versions past that have the gate's own clock.
    Checked on 2026-11-23 with this code against the real proxy and
    index: `golang.org/x/mod` v0.2.0, which `TestLiveIndexNotFound` does
    not find in the pages from its commit time, is found on the first
    page read (`TestLiveStored`, opt-in), and so was each of the three
    versions above, with the real budgets. The recorded tests replay the
    proxy's and the index's answers for four versions of
    `golang.org/x/mod` and `golang.org/x/text`. Also in this change: a
    version read part-way when the run's pages ran out no longer says
    "not looked up", it says how many pages were read. Not built: asking
    the index for fewer lines at the header's time, which would make
    such a read several times faster.
62. **Publish does not merge onto a base that changed the pull
    request's files.** The owner chose it on 2026-11-23, in its minimal
    form. Every fact is about the pull request's head against the commit
    it branches from, and a merge puts that head on the default branch
    as it is now. Two pull requests that each edit one lock file can
    merge one after the other, the second without a conflict, into a
    lock that neither proposed. For npm that can be a lock npm itself
    calls invalid: two packages that pin each other's exact version,
    each moved by a pull request of its own. Required checks can pass on
    such a lock. Publish merges one pull request after another
    (amendment 18), several ripen in one scheduled run, and Dependabot
    takes minutes to rebuild a sibling, so the gate would do this
    unattended.
    Now, when the decision is to merge, publish first reads the pull
    request's file list (`pulls/{n}/files`) and GitHub's comparison of
    the head with the default branch (`compare/{head}...{default}`:
    `ahead_by` and `files`). When the default branch is ahead and names
    a file the pull request changes, by `filename` or
    `previous_filename` on either side, or lists 300 files (GitHub's
    cap, where the list is cut short), no merge is attempted. The pull
    request waits as for a base branch that moved (amendment 17:
    `checks_pending`), the scheduled run looks again, and at the wait
    deadline it is `person` (`checks_deadline`). A pull request that is
    only behind merges as before. The gate does not rebase, update or
    comment to bring a pull request up to date. Dependabot rebuilds such
    a pull request itself in most cases, though not one older than 30
    days, and the new head gets a run of its own.
    The comment's lead is the gate's own for this wait: it says that
    GitHub was not asked, names the file, and says what ends the wait,
    without spelling a command Dependabot would act on. The two reads
    come before the status that says success, so neither a held merge
    nor a read that failed leaves a success on an unmerged head. A read
    that fails, an answer without `ahead_by` or without `files`, and a
    pull request GitHub lists no file for are errors: nothing is merged,
    the job fails, and on an event publish reports a run that could not
    decide (amendment 15).
    What it costs. Each held pull request that Dependabot rebuilds costs
    one more CI run and one more gate run with its model calls. Siblings
    that edit one file (two actions pinned in one workflow or recorded
    in `actions.lock`, two modules in `go.sum`) merge one for each
    rebuild, where they merged in one run. A held pull request that
    Dependabot does not rebuild waits in silence until the wait
    deadline, a security fix among them. Telling the owner sooner (a
    reason of its own at the second hold of one head) was weighed and
    not built.
    Limits. The look and the merge are separate calls: a push that
    reaches the default branch between them is not seen. Publish jobs
    run one at a time, so that push is somebody else's. Merges by hand
    are held by nothing. A change on the default branch that touches
    none of the pull request's files is not held, whatever it does to
    them. The commit status and the notification at the deadline carry
    the reason's code and sentence, which speak of required checks; only
    the comment says what happened.
    Not verified: no publish job has run this on GitHub. Read by GET on
    2026-11-23: the comparison's shape on a public repository (both
    members always there, `files` empty when the head lacks nothing, 300
    files and no more for a long history).
63. **A veto the gate recorded stands.** Found by the adversarial
    review, by two reviewers. A verdict is keyed by what was read, not
    by the pull request or its head, and an event's run always asks the
    model again (amendment 39). Publish decided on that run's verdicts
    file alone and wrote the comment's memory from it alone. So a veto
    lasted until the next rebase: Dependabot rebases a pull request
    whenever the default branch moves, the content and its key stay,
    the model is asked again, and one answer of `no_veto` merged code
    the gate had told the owner about. Nothing fixes the model's
    sampling, so a second answer need not be the first. A run whose
    review job gave no answer lost the veto as well: the pull request
    waited, the comment remembered nothing, and the next clean answer
    merged. The same held on the schedule for a wait that followed.
    Now publish reads the gate's own comment at every decision, and a
    veto it remembers for a prepared read's content key, under the
    reviewer fingerprint publish computes, counts whatever this run's
    verdicts file says for that key: no veto, no answer, a refusal to
    take the read, or nothing. When this run's file has a veto too, that
    one counts (it is the same outcome, with the model's fresh quotes).
    A veto in this run's file counts over a clean verdict the comment
    remembers, as it always did. The comment's memory is written from
    the verdicts so joined, vetoes first, and a veto for content the
    pull request no longer has is kept as well, so that a pull request
    rewritten to another version and back meets it again. A marker that
    holds more than its 100 verdicts drops clean ones. The run that
    could not decide (amendment 15) already kept the memory whole.
    The event's run still asks the model: what changed is that its
    answer cannot take an objection back. This holds on an event and on
    the schedule alike.
    What gets past a veto. A person, who merges or closes the pull
    request by hand: the comment says so, and says that running the gate
    again does not. Content with another key: a new version, or the same
    version rebuilt to other bytes. And a reviewer with another
    fingerprint (amendment 11): a new prompt, answer schema, model or
    effort is another question, and nothing remembered under the old
    one is looked at. That is the owner's own change, made in the gate's
    repository.
    How it shows. The update's Veto row names the model "in an earlier
    run" as its source when the veto is the remembered one, with the few
    quotes the comment keeps (three, cut to 300 bytes). The hint of the
    reason `veto` says that the gate does not take a veto back. Each new
    head is still notified once, as for any `person`.
    What it costs. A veto that was wrong now needs the owner once for
    the pull request, where a rebase could clear it before: by design.
    Publish reads the comment at every decision, also for a pull request
    with nothing to remember, and decides nothing while GitHub does not
    answer for it; on an event that is a run that could not decide
    (amendment 15). No decision becomes more permissive.
    Limits. The memory is the comment's marker. A marker this version
    cannot read remembers nothing, and neither does a pull request
    Dependabot closed and opened again under a new number. Whoever can
    edit the gate app's comment can remove a veto; such a person can
    also merge.
64. **The scheduled run asks the model.** The owner agreed to it on
    2026-11-23 and changed both federation rules to admit the event
    `schedule` beside `workflow_run`. This replaces "no model call on a
    schedule" in sections 7 and 8, narrows amendment 39 and moves
    amendment 16's notice. Before it, a read the model had left
    unanswered waited until a person ran the gate again, and so did
    every read whose verdict was remembered under an older prompt or
    model: seven days, then `person`.

    is a second review job, with a command of its own (`dep-review

    only after checking it against refresh's checksum, and uploads its

    version reads, with the outcome `wait`, for the head the pull
    request has now; when the comment remembers no verdict for the read
    under the current reviewer fingerprint; and when an ask is due. A
    head the gate has not written for yet (a rebase since the wait, and
    since amendment 66 a pull request the schedule looks at for the
    first time) is evaluated once with no model, which gives the count
    below a place to be kept before anything is spent; it is asked about
    at the next run.
    The skip list. The refresh job writes `answered.json` beside each
    pull request's facts: an entry for every prepared read that is not
    to be asked about in this run, because the comment remembers an
    answer or because no ask is due. It has the verdicts file's form,
    and every entry is read `none` under the current fingerprint, with
    no veto: reread takes the keys from it and nothing else, and read as
    a verdicts file it says that nothing was read. reread writes a
    verdicts file for a pull request only when it put a read of it
    before the model, so a file means the model was asked. A list that
    is missing or does not decode means nothing of that pull request is
    asked about.
    Where a verdict comes from. Publish takes no verdict from the
    refresh job, which no longer writes a verdicts file. It reads its
    own comment and joins what that remembers with what reread wrote in
    this run: a remembered clean verdict counts for a read this run has
    no answer for, an answer of this run counts over it, and a veto
    stands (amendment 63). So the job that parses what a pull request
    wrote can make a read wait, or make the model answer a question
    twice, and can never make a read count. That is stricter than
    before, when publish decided on the copy of the comment's memory
    the refresh job handed it. On an event's run a remembered clean
    verdict still does not stand in for an answer the review job did not
    get (amendment 39).
    Spacing. The marker counts the scheduled runs that asked for its
    head (`asks`) and when the last one did (`asked_at`), whatever the
    answer. The first ask is due at once, the next 30 minutes after it,
    and each one after that after twice as long: 1 hour, 2 hours, and so
    on. That is nine asks in the five and a half days after the first,
    inside the wait deadline of seven; an ask at every half-hourly run
    would be 336. An event's run writes a count of none, a scheduled run
    in which reread wrote a file for the pull request adds one, and any
    other scheduled run carries the count over for the same head. When
    publish cannot decide a pull request after the model was asked, it
    rewrites the marker line alone to count the ask, so that a pull
    request that fails at every run is not asked about at every run. The
    count is not reset by a new fingerprint: a verdict under an older
    prompt or model is simply not on the skip list, and the read is
    asked about when the count allows, which for a read that was
    answered before is at once.
    The notice. One miss needs nobody. When the second scheduled ask for
    a head also leaves a prepared read without a verdict, the owner is
    told, once per head: the model has not answered, the gate keeps
    asking, and nothing needs doing unless the reviewer is down for
    good. The event's run no longer sends a notice and no longer says to
    re-run all jobs for this. A notice that could not be sent is sent by
    the next scheduled run that decides the pull request.
    A token exchange that is denied is a miss like any other: the review
    job has no credential, writes read `none` for the read, and the ask
    is counted. So a gate pinned before the rule admits `schedule` waits
    and backs off, and merges nothing unread.
    What changes for a pull request. A reviewer that did not answer on
    the event's run is asked again within half an hour and the pull
    request needs nobody. A verdict remembered under an older
    fingerprint is asked for again at the next scheduled run. Both were
    waits that only a person or the deadline ended. The decision table
    does not change, and no `person` becomes a merge without a model's
    answer under the current fingerprint.
    What it costs. In a scheduled run that asks, publish waits for the
    asking: the merges of that run that are only waiting for an age are
    held for minutes, at worst for reread's 120. From gathering to
    deciding a scheduled run may now take 2 h 45 min of timeouts, inside
    the 4 hours of amendment 52. The marker has two more members, and a
    build from before this amendment does not read a marker that has
    them.
    Limits. A reread job that dies before its artifact is uploaded (a
    lost runner, a failed upload) is not counted, and the next run asks
    again at once; the command writes what it has when its own budget
    ends, so that takes a failure of the job itself. Whoever can edit
    the gate app's comment can reset the count. The refresh job can make
    reread ask about every read at every run, by an empty list; that is
    a cost and not a decision, and it takes the job's token.
    Not verified: a scheduled run's token being admitted by the rule,
    and a scheduled run that ends with a real verdict. No GitHub page
    shows a token of a job in a reusable workflow that a scheduled
    workflow of another repository calls; the claims the rule looks at
    (`repository_id`, `repository_owner_id`, `ref`, `job_workflow_ref`)
    are documented as the same for `workflow_run` and `schedule`, both
    of which run the default branch's workflow, and `event_name` as the
    one that differs. A denied attempt shows the token's claims in the
    Console's authentication history. What the tests run: the layout
    (`cmd/dep-review/workflow_test.go`), the exchange against a server
    that denies it, ending as a counted miss, and every rule above.
65. **A Bound whose source did not answer is waited for.** This
    replaces amendment 41, which recorded the opposite as built and left
    the rule to the owner. It is the more permissive rule: a `person`
    becomes a `wait`. The owner agreed to it on 2026-11-23 as a part of
    the scheduled run that asks the model (amendment 64), whose design
    names this row; without that run a later evaluation could gather the
    update but had no model to read it with.
    When the source of an update's Bound does not answer (the module
    proxy, the npm registry, GitHub), the fact is unavailable and the
    gatherer names no artifact, since there is no verified hash to fetch
    one against. The fetch job now records such an update's read as
    `unavailable`, with the gate's sentence that the pin's source did
    not answer, where it recorded `nothing`. For npm the tarballs' half
    of NoRegress is unavailable with it, where it was "not looked at".
    `wire.Join` makes that Read `none`, and `allow.Decide` answers
    `wait` (`source_unavailable`, `read_pending`) until the wait
    deadline. Neither function changes. The next scheduled run gathers
    again; once Bound holds, the read is prepared and the model is asked
    about it in that same run (amendment 64). At the deadline the pull
    request is `person` as for any source that never answered.
    What stays `person` at once: a Bound that was answered "no" (the
    registry serves another hash, the tag resolves elsewhere), a Bound
    nobody gathered, and a pin that is bound while the gatherer names no
    artifact for it (an old version with no hash to check against):
    `read_unknown`, as before. Nothing is read or merged on the strength
    of this rule: the update still needs Bound to hold and a read under
    the current fingerprint before it can merge.
    Limits. As recorded by the research this rests on, with the real go
    command against a proxy that answered 503: an update of a module
    the repository already has waits, and a new unlisted module still
    goes to a person (`name_created_unknown`), because the go command's
    error for a version list is not one of the shapes the gatherer
    reads as an outage. That run was not repeated for this change; the
    test here drives the fetch job with a gatherer that returns the
    unavailable Bound, for Go, npm and Actions.
66. **The schedule evaluates a pull request the gate has nothing for.**
    Found by the adversarial review (two findings), and needed at
    cut-over. The scheduled job looked only at pull requests whose gate
    comment says `wait`. A Dependabot pull request with nothing from the
    gate for its head was looked at by nothing: no status, no comment,
    no notification, until Dependabot pushed again. That is what an
    event's run leaves when it dies before publish (the build or the
    classify job fails, classify runs out of time), when the publish job
    fails before the binary runs (the artifact download, a checksum, the
    app token, the `app_slug` check), and when the head moves on from a
    `person`, a merge or a failed run and the new head's run is one of
    those. A comment whose marker this version cannot read, which is
    every pull request open when v0.1 is replaced, was reported and
    failed every scheduled run (amendment 36) until a person started a
    new run for each.
    Now `land.Schedule` lists, besides the waits, every open pull
    request by `dependabot[bot]` from a branch of the repository for
    whose head the gate has nothing: no gate comment, a gate comment
    with no marker this version reads, or a marker for another head that
    does not say `wait`. The refresh job evaluates such a pull request
    from scratch, exactly as a wait: the identity proof, the facts, and
    publish with its own proof. Nothing in a comment this version cannot
    read is believed (its first-seen times start again); a marker it can
    read for an older head still gives what a marker gives, the vetoes
    and verdicts by content key and the first-seen times by pin. No
    model is asked in the run that first evaluates a head: reread asks
    only for a head this version's marker is for (amendment 64), so the
    first run writes that marker and the next one asks. A pull request
    classify does not call the gate's (an ignored ecosystem) is left
    without a comment as always. It is listed at every run for that, and
    costs the proof each time and none of the places below.
    A marker for the head that says anything but `wait` is a decision,
    and the pull request is not listed. That includes the report of a
    failed run: the owner was told what to do (amendment 15).
    The work of one run is bounded, in five ways.
    A pull request is listed only when it has not changed for four hours
    (`updated_at`; `land.UndecidedAfter`, which is `MaxFactsAge`). A push
    starts an event's run, and after that long the run is not going to
    decide, so the schedule does not race it or ask the model beside it.
    At most five such pull requests are evaluated in one run
    (`maxUndecided`), lowest number first, counting the ones the job
    gathered facts for or failed on; the rest are the next run's. They
    are taken before the waiting ones, which is why they are capped. Everything shares the refresh command's 25 minutes, and what
    is not reached is the next run's. No model is asked in the first
    run. And a head is tried once: when the refresh job cannot evaluate
    it, or publish cannot decide it, publish reports the run as one that
    could not decide, on its own reading that the pull request is
    Dependabot's, open and still has nothing for that head, and after
    its own identity proof: status `error`, the comment, one
    notification. The marker then says `failed` for the head, and the
    schedule leaves it alone. The comment of such a report names what
    works for it, a person or a new head, and not "re-run all jobs":
    running a scheduled run again evaluates nothing for it. A proof
    GitHub did not let publish finish is not reported, and neither are
    facts publish came to more than four hours late (amendment 52): the
    next run tries again. For publish to know that a pull request was tried, the
    refresh job leaves its directory in the artifact with one file and
    no facts.
    Jobs. The refresh job no longer fails for one pull request, and the
    step that failed it when nothing was uploaded is gone: whenever a
    pull request could not be evaluated publish runs, and its last step
    fails the run (amendment 18). The job's `publish` output is true
    when publish has something to do, which since amendment 67 is more
    than an upload, and a new step output, `upload`, says whether there
    is an artifact. Both are hints from a job without the app's token:
    wrong, they cost a run or a wait, and what publish writes it writes
    on its own reading.
    What it costs. A pull request whose event's run died waits four
    hours for the schedule, a security fix included; before, it waited
    for a person who had no way to know. A pull request that is rebased
    after a `person` and whose new run dies is evaluated again, which is
    what the run would have done. Other activity on a pull request (a
    comment, a label) moves `updated_at` and puts the schedule off.
    At cut-over. The pull requests v0.1 left open are evaluated by the
    first scheduled run of this version, five in a run, whatever v0.1
    said of them, including the ones it sent to the owner; the run after
    asks the model. One that is past its wait deadline when first
    evaluated (opened more than seven days, plus its required age, ago)
    and has a read to wait for is `person` at once (`read_deadline`),
    before any model was asked: the deadline counts from the pull
    request, not from the gate's first look. Having Dependabot recreate
    it gives it an event's run.
    Limits. A scheduled evaluation that fails for a passing reason (the
    registry's tool output, a GitHub error that outlasts the client's
    retries only in refresh) costs the owner a look: one try, then the
    report. Five failing pull requests in a run are reported in that run
    and free their places. What moves `updated_at` was not measured.
    Not listed: a pull request not authored by `dependabot[bot]`, and
    one from a fork, as before.
67. **A wait reaches its deadline, and a notification is sent, whatever
    fails.** Found by the adversarial review (two findings). Two things
    the gate promised happened only when a later run got through.
    The deadline. `allow.Decide` makes a retry's wait `person` at the
    wait deadline, and a wait for an age merges or goes on to a deadline
    of its own; but only a run that decides says so. A waiting pull
    request whose refresh failed at every run (the fetch failures of
    section 12, a proof that never finishes), or that publish could not
    decide, kept its `wait` comment for good. Every scheduled run was
    red, and nobody was told on the pull request or by notification.
    Now a scheduled publish, after it has decided what the refresh job
    wrote, lists the open pull requests itself with its own token. A
    gate comment that still says `wait` with a deadline that has passed
    is one this run did not decide, since a decision rewrites the
    comment. Publish makes it a person's (`land.Expired`): status
    `failure`, a comment that says the deadline passed with nothing
    newer known and nothing found against the update, one notification
    per head, and a marker that says `person` for the head the pull
    request has now, with everything the comment remembered. The
    identity proof does not stand in the way: publish runs it, and only
    an answer that the pull request is not the gate's any more (closed,
    a newer head by the proof's reading, an ignored ecosystem) leaves
    the wait alone; an error, an unfinished proof and "not Dependabot's
    alone" are a person's all the same. The refresh job's `publish`
    output is true whenever it saw a wait past its deadline, so publish
    runs also when nothing was uploaded, and a missing refreshed
    artifact is no pull requests to decide, not an error.
    The notification. A notification that fails to send is returned as
    an error after the comment and the status were written, and the head
    is not remembered as told. The code said that the next run sends it.
    No run did: a `person`, a refused merge and a failed run are not
    evaluated again, so the owner's one notification for exactly the
    outcomes that need a person was lost with three bad answers from
    Pushover. Now the same look finds every gate comment that records
    such an outcome for the pull request's head and no notification for
    it, and publish sends one (`land.Tell`): a fixed sentence that
    points at the comment, since the marker keeps the outcome and not
    the reason. When it is delivered the marker line alone is rewritten.
    The refresh job's `publish` output is true for such a comment too.
    The notice about a reviewer that does not answer needs none of
    this: the wait is decided again at every run (amendment 64).
    With notifications turned off (no Pushover secrets) a head now
    counts as told and is remembered so. Otherwise every such comment
    would read as owing a notification and bring publish back at every
    run. A repository that turns notifications on later is not told
    about what was decided before.
    Limits. A wait with no deadline (amendment 22: nothing to count
    from) never expires this way. A deadline is the last decision's, so
    a wait that was last decided long before its age was reached expires
    seven days after that age, as it would have had every run failed
    from then on. If the comment cannot be rewritten after a
    notification was delivered, the next run sends it again. When the
    refresh job itself fails (it cannot list the pull requests), publish
    does not run: the run is red and nothing else happens until a run
    gets through. And a notification is still owed while Pushover stays
    down: each run tries once more and fails.

## 12. Where input is parsed by hand

Read from the code as it was after the trim pass, and again, file by
file, after amendments 51 to 67 (both on 2026-11-23). "By hand"
means the gate's own code takes the bytes apart: a regular expression, a
split, a walk over archive entries or JSON tokens, or its own rule for
what a decoded value may be. What a real tool or a vetted library reads
whole is not listed: `go.mod` (`x/mod/modfile`), version order and module
paths (`x/mod/semver`, `x/mod/module`, `go/version`), module zips
(`x/mod/zip`, `dirhash`), the lock's dependency tree (`npm ls`), a
module's hashes, retractions and version list (the go command), a diff
(`git diff`), and JSON decoded into fixed types (`encoding/json`). A
mismatch ends in one of four ways, and none of them is a merge: `person`;
a wait; the gate's own clock for a time no registry gives (amendment 38);
or a failed job, which publish reports as a run that could not decide
(amendment 15). One input only says where another is read from: the
proxy's `Last-Modified` for the Go index (amendment 61). A mismatch there
sends the reader to the place it started from before, and what it reads
from there ends as the index's row says.
